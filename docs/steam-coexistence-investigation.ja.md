# Steam起動中の切り替え調査

> この文書は改名前のRemapconで実施した調査・試験の記録です。旧名称・実行file・TEMP pathは履歴として保持します。現在の製品名はPadMuxです。[名称変更と互換性](padmux-rename.ja.md)。

## 確認できたこと

Steam起動中にRemapconがコントローラーを共有アクセスで開く試験を行った。対象アプリを前面にしてXボタンを押すと、Remapconで割り当てた入力に加え、Steamのオンスクリーンキーボードが開いた。これは二重入力であり、目的の動作ではない。試験用の共有アクセス設定は取り下げた。

Steamのデスクトップレイアウトを常時「空」にすれば、この症状を隠せる場合がある。しかし、対象アプリから離れたデスクトップでもSteamの割り当てが使えなくなる。対象アプリの前後で自動的に所有者を切り替えるという要件を満たさないため、解決策として採用しない。

共有HIDハンドルはRemapconがレポートを読む手段であり、Steamが同じ入力を解釈・送信することを止めない。コントローラー側のLizard Modeを無効にする処理も、SteamのDesktop Layoutやオンスクリーンキーボードの出力を止めるものではない。

## 排他取得の試験実装

[SteamlessController v1.18](https://github.com/ddeverill/SteamlessController/releases/tag/v1.18)は、排他取得に失敗したときにWindowsのデバイスを一度無効化・再有効化して、SteamのHIDハンドルを解放させる実装を持つ。対象アプリを離れるときはRemapconがハンドルを閉じ、再びデバイス到着を発生させてSteamへ返す。取得側にはSteamより早く排他ハンドルを開くための待機処理もある。v1.18の実装にも共有アクセスへのフォールバックがあるが、Remapconでは二重入力を成功扱いにできないため採用しない。

試験ブランチには、管理者として起動した場合だけ使える「対象アプリの前面でコントローラーを排他取得する」設定を追加した。排他取得に失敗すると、自分のHIDハンドルを閉じ、別プロセスで対象のコントローラーデバイスを無効化・再有効化する。デバイスが戻ったときに排他ハンドルを取得できた場合だけ、Remapconの割り当てを有効にする。共有アクセスへのフォールバックはしない。対象アプリから離れたらキーを解除してハンドルを閉じ、もう一度デバイスを再認識させてSteamへ返す。

無効化するデバイスのIDは管理者だけが書けるレジストリに記録し、再有効化を確認してから記録を消す。処理が途中で止まった場合は次回起動時に再有効化を試みる。取得失敗後は20秒待ってから再試行する。中断後の復旧や取得失敗時の再試行は、実機ではまだ確認していない。

## 実機確認の合格条件

1. 試験版ZIPを別フォルダに展開し、設定をエクスポートしてから、Remapconを管理者として起動する。「前面で自動有効」と「対象アプリの前面でコントローラーを排他取得する」をオンにする。SteamのDesktop Layoutとガイドボタン設定は普段の状態のままにする。
2. 対象アプリの前面では、Remapconの割り当てだけが動き、Steamのキー・マウス入力やオンスクリーンキーボードは出ない。
3. 対象アプリから離れると押下中のキーが解除され、SteamのDesktop LayoutとSteamゲーム内のSteam Inputが元どおり動く。
4. 前面切り替えを繰り返しても、コントローラーが無効状態で残らない。USBとPuckの使用する接続方式でそれぞれ確認する。

Windows CIでビルドとZIPの検証は成功した。実機では、対象アプリを最前面にするとSteam側でコントローラーが切断扱いになり、Steamのオンスクリーンキーボードが出ず、Remapconの割り当てが動いたとの報告があった。対象アプリから離れるとSteamのDesktop Layoutも動いた。当初は「ボタンを探す」がSteam起動中に反応しなかったが、確認中も一時的に排他取得する修正版で動作したとの報告があった。Steamゲーム内のSteam Input、前面切り替えの繰り返し、USBとPuckの各接続方式での動作は引き続き確認が必要。v1.5.0で試験的な設定として公開した。試験中にコントローラーが反応しなくなった場合は、Remapconを終了して再起動する。復旧エラーが出た場合はWindowsのデバイスマネージャーで対象のHIDデバイスを再度有効にする。
